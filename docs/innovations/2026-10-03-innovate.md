# Innovations for Marshall

2026-10-03 - generated by /innovate, with two wants from Jacques as input: file issues from the phone, and handle PRs that build on each other.

**TLDR:** Marshall already has most of the parts for both wants, but two facts block them today.
Marshall ignores Linear's "blocked by" links, so on 2026-09-22 it started nine dependent issues at the same time, and all nine failed as draft PRs.
Marshall has also been paused since 2026-09-30, so an issue filed from the phone would wait with no answer.

## What this product is

Marshall is a Linear autopilot that runs on Jacques's laptop.
It polls one Linear team every 45 seconds for Todo issues assigned to Jacques, claims each one, and runs Claude Code agents through plan, implement, review and hand-off until a pull request is ready.
Jacques then reads the hand-off comment while the issue is in Needs Verification, and he merges the PR (Marshall marks the issue Done) or bounces it (comment, move to Todo, Marshall replans).

**Assets it holds**

- The `events` table in `~/.marshall/marshall.db` records every phase change, stall, rebase, merge and hook event, but only the ntfy notifier reads it, for six event types (`PUSH_EVENTS` in `src/notify.ts`).
- `IssueById` in `src/linear/queries.ts` already fetches Linear `relations` and `inverseRelations`, but `toDetail` in `src/linear/map.ts` drops the relation `type`, and nothing reads the result.
- Merge machinery: `pollMerges`, `queueSiblings`, `startNextRebase` and `startResolver` in `src/phases/rebase.ts`, plus `sweepDone` and `markDone` in `src/phases/done.ts`.
- Every plan has a `## Likely touched files` section (`plugin/skills/plan/template.md`) that no code reads.
- An ntfy.sh push channel (`sendPush` in `src/notify.ts`) is the only thing that reaches the phone today.

**Frictions it lives with**

- There is no inbound surface: polling only, a personal API key, no webhooks, and no Agents API (`delegate` waits for "the iteration 2 OAuth agent", header of `src/linear/client.ts`).
- Pickup needs an exact shape: team `teamId`, assignee = the key's user, state Todo (`PickableIssues` in `src/linear/queries.ts`).
- There is one PR per issue, always based on `config.baseBranch`.
  A draft PR only means failure (`plugin/skills/implement/SKILL.md:163-173`), and nothing ever calls `gh pr ready`.
- `fileFollowUps` is off, because the dry run filed 24 follow-ups from six one-line issues (`src/config.ts:63-69`).
- `finishClaim` (`src/scheduler/store.ts:147`) wipes retry history on a bounce, the hand-off sidecar keeps only the latest round, and no head SHA is stored.

## The five

| Tier | Idea | The bet in one line | What to prove first |
|---|---|---|---|
| 1 | Phone intake with receipts | Phone-Claude files the issue in the exact shape Marshall picks up, and Marshall answers with a push | That Marshall is running when Jacques is away |
| 2 | Obey "blocked by" | Do not start an issue until every issue that blocks it is Done | That Jacques keeps linking issues in Linear |
| 3 | The train | Start a child issue on top of its parent's open PR, and throw the children away if the parent is bounced | That a child built on an unreviewed parent is seldom bounced because of the parent |
| 4 | Earned auto-merge | A kind of issue that Jacques keeps merging clean stops needing his review, with spot checks | That Jacques's merge click measures quality |
| 5 | Nothing to write (moved to tier 3) | Marshall builds the follow-ups Jacques ticks, and drops what he ignores | That a three-line push costs Jacques less than writing the issue |

**The one I would fund:** Obey "blocked by".
It is about 30 lines of production code plus tests.
It would have stopped the failure of 2026-09-22, where Marshall started TOD-6 to TOD-14 at the same time although Linear already had the "blocked by" links (TickTick `docs/planning.md`: "Each issue has 'blocked by' relations that match the graph above").
It is also the base that the train (tier 3) needs.
Ship the stale-draft fix in the same PR.

## Tier 1 - Phone intake with receipts

> You tell Claude on your phone what to build, it files the Linear issue in the shape Marshall looks for, and Marshall pushes "got it" to your phone, or tells you why it cannot start.

**Today** `PickableIssues` (`src/linear/queries.ts:115-130`) takes only issues in team `teamId`, assigned to the API key's user, in an `unstarted` state, and without `human-only`.
An issue from the phone that lands in Triage or Backlog, or has no assignee, is invisible.
When Marshall does not start an issue, it sends nothing: the log has 816 cap skips, and none of them made a push.
The iteration 3 plan wants "iOS Shortcut → webhook → Linear issue" (`docs/project_marshall_plan.md:335`).

**Instead** Step 1 needs no code.
Add a Claude Project on claude.ai with the Linear connector and this instruction: team TOD, `assignee: "me"`, state Todo, and a brief with goal, acceptance criteria and likely files.
The Linear MCP `save_issue` tool accepts all of these fields, so the issue matches the unchanged `PickableIssues`.
Step 2 is the code worth writing: receipts.

- `picked_up` when Marshall claims the issue.
- `queued`, with the `check.reasons` text that `consider` already makes (caps, slots, pause).
- `stuck`, when the same issue fails to claim again and again.
  On 2026-09-29 one Todo issue with a leftover `marshall/agent-0` label failed to claim 282 times, and nothing was sent.
- `paused`.
  `tick` returns before `listPickable` when Marshall is paused, so the receipt check must run before the pause check.

Step 3 is a heartbeat.
Ping a dead-man's switch such as healthchecks.io on each pulse, so that the phone gets a push when pulses stop.
Also post each receipt as a Linear comment, so phone-Claude can read it back.

**Standing on** `PickableIssues` in `src/linear/queries.ts`, `PUSH_EVENTS` and `eventsAfter` in `src/notify.ts`, `consider` in `src/scheduler/tick.ts`, `claim` in `src/linear/client.ts`.

**Why now** The Claude iOS and Android apps use remote MCP connectors, and Linear's official MCP server (`mcp.linear.app`) creates issues with all fields.
That removes the webhook the iteration 3 plan wanted, before anyone built it.

**The hard part** There are two small traps.
`eventsAfter` reads only `master.%` rows and gets the title from `claims`, so a receipt sent before the claim must carry the identifier and title in its own payload.
Also leave "plan model" out of the receipt: the classifier runs after the claim, and it failed 7 of 33 times.

**What already exists** Linear agent sessions (June 2026) let Cursor, Codex and Devin take issues from the Linear mobile app.
The Agents API makes an agent answer within 10 seconds, so those tools have a receipt built in.
They run in the cloud.
The wedge is a receipt about local state (slots, caps, pause, asleep) for a loop that runs on Jacques's own laptop and plan.
Linear has no native voice or Siri issue creation.
Claude voice mode can use connected tools (July 2026), but remote MCP in voice is not documented: claude-ai-mcp issue #146 was closed "not planned", and #1099 says approval prompts may not show in voice.
Use dictation into a text chat.
Web search was available.

**The load-bearing risk** Marshall must be running while Jacques is away.
Since 2026-09-20 the log has pulses in about 10% of 10-minute buckets, on 6 of 14 days.
The `paused` flag has been set since 2026-09-30T15:51Z, and no launchd service is loaded.
`caffeinate -i` does not keep the laptop awake with the lid closed.
Trust note: the Linear MCP files issues as Jacques's own OAuth identity, so anything that holds his tokens can start a `bypassPermissions` run, which is already true today.
Keep `save_issue` on "Needs approval" in the Claude app.
The ntfy topics are public, so receipts leak issue titles, the same as today's pushes.

**Cheapest proof** Add the Project instruction (about 1 hour), run Marshall as usual for 7 days, and file every phone idea this way.
Then compare each issue's Linear `createdAt` with `claims.claimed_at`.
If fewer than half are claimed within 10 minutes, the problem is uptime, not intake: build the heartbeat first and the receipts after it.

## Tier 2 - Obey "blocked by"

> If issue B needs issue A, Marshall waits, and starts B only when A's PR has merged.

**Today** Marshall ignores Linear relations.
`IssueById` fetches them, `toDetail` drops the `type`, and `PickableIssues` does not ask for them.
On 2026-09-22 Marshall claimed TOD-6 to TOD-14 in parallel while TOD-5 (the scaffold) was still running.
All nine stopped with "unmet dependency", their PRs (#3 to #11) became drafts and were closed, and Jacques finished the chain by hand (#13 to #21).
This is where the belief "Marshall marks blocked PRs as drafts" comes from.
It does not do that.
A draft only means the agent failed (`plugin/skills/implement/SKILL.md:163-173`), and those nine failed because their parent was not there yet.
When a PR merges today, Marshall only rebases every other waiting PR onto `master`, one at a time (`queueSiblings`, `startNextRebase`).

**Instead**

- Add `inverseRelations { nodes { type issue { identifier state { type } } } }` to `PickableIssues`.
  The blocker is the child's *inverse* `blocks` relation, which is a known trap.
- Map open blockers in `toPickable` (`src/linear/map.ts`).
- In `consider` (`src/scheduler/tick.ts`), skip the issue with the reason `waiting_on TOD-x`, and show it in `marshall queue` and in the tier 1 `queued` receipt.
- Green means the blocker's state type is `completed`.
  `canceled` stays red and shows in the queue, so Jacques decides.
- No new columns are needed.
  `markDone` on merge turns the light green, and `worktrees.create` already branches from a fresh `origin/master`, so the child plans against the parent's real code.
- Ship the stale-draft fix with it: in implement skill step 9, a green result on an existing draft runs `gh pr ready` and removes `## Still failing`.

A fallback for missing links came from the footprint research: all nine plans from 2026-09-22 named their dependency in prose.
A `needs:` line in the plan template could catch a link that Jacques forgot.
Build it only if missing links turn out to be common.

**Standing on** `IssueById` and `PickableIssues` in `src/linear/queries.ts`, `toDetail` and `toPickable` in `src/linear/map.ts`, `consider` in `src/scheduler/tick.ts`, `markDone` in `src/phases/done.ts`, step 9 of `plugin/skills/implement/SKILL.md`.

**Why now** The TickTick dependency graph and its Linear links already exist, and the first real batch failed on exactly this.
Iteration 1 has one meaning for "draft", so this is the cheapest time to keep it that way.

**The hard part** None technical, this is a priority question.
The research put the effort at tier 1: about 30 production lines plus tests.
It stays in the tier 2 slot because it is a missing piece, not a sharpening of something that ships.

**What already exists** GitHub native stacked PRs (public preview 2026-07-30), Graphite and git-spice manage PRs, not the order in which an agent starts work.
Graphite and git-spice handle trees, not diamonds, and TickTick has diamonds: TT-4, TT-7, TT-9 and TT-11 have two parents.
The wedge is that Marshall can schedule the whole Linear dependency graph.
Web search was available.

**The load-bearing risk** Jacques sets the pace.
A strict gate queues each level behind his merges, and TickTick's graph is 7 levels deep.
Merges took 3 to 28 minutes on 2026-09-22 to 24, but PRs #16 to #21 waited 3 to 4 days and then all merged within about a minute.
With batch review, Marshall sits idle between levels.
Tier 3 is the answer to that.

**Cheapest proof** Two days.
Make three small linked issues A → B → C plus an independent issue D.
Pass: D starts at once, B is not claimed while A waits for review, and B is claimed within 2 pulses of A's merge.
Log the idle time per level, because that number decides whether tier 3 is worth building.

## Tier 3 - The train

> Marshall starts a child issue on top of its parent's unreviewed PR, so the whole chain is ready for one batch review; if the parent is bounced, the children are thrown away and rebuilt.

**What moved** This idea came from the graveyard.
A generator proposed it at tier 5 as "no base branch, only the train": every new job sits on top of all the work still waiting for review, in claim order.
The research found that claim order is the wrong shape (TT-6 would sit under four cars that do not use it), changed it to follow the Linear graph, and put it at tier 3.
It took the tier 3 slot from footprint locks; the graveyard says why.

**Today** Each claim starts from `master` (`baseBranch` in `marshall.config.json`, `MARSHALL_BASE_BRANCH` in `src/isolation.ts`).
Jacques has already run a train by hand.
In TickTick PRs #16 to #21, each head is an ancestor of the next (5 of 5 checked), all have base `master`, and they merged in creation order within 73 seconds with zero rebases.
Building the six took 9.2 hours, and each one waited 84 to 93 hours for review.

**Instead**

- Pick: an issue is pickable when every "blocked by" parent is Done or parked in `awaiting_human`.
  This extends the tier 2 gate.
- Base: `master` if all parents are merged, the parent's head if one parent is unmerged, and an octopus merge of both heads if two are unmerged.
- PR target: always `master`.
  TickTick has `deleteBranchOnMerge: false`, and Jacques merges about 12 seconds apart while Marshall polls every 45 seconds, so a PR based on the parent's branch would merge into a dead branch.
  The hand-off names the parent PR, so the reviewer knows which part of the diff is the child's own work.
- Bounce: close and re-queue every claim whose branch contains the bounced car (`git merge-base --is-ancestor`).
  Do not replay them.
- Cap: at most 3 cars deep.
- `src/phases/rebase.ts` stays, because independent issues still need sibling rebases.

**Standing on** TickTick PRs #16 to #21, `queueSiblings` and `startNextRebase` in `src/phases/rebase.ts`, worktree creation in `src/worktree.ts`, the `claims` table, the tier 2 gate.

**Why now** Marshall's median review wait is 36 minutes (n=9), but chain PRs waited days.
That idle time is real and measured, and GitHub now ships stacks, so reviewers expect this shape.

**The hard part** Semantic coupling.
A child can stay green after its parent changes and still be wrong.
The bounce rule (throw away, do not replay) avoids this at the cost of rebuild time.

**What it needs that does not exist yet** A `claims.base_ref` column, an octopus-merge step in worktree creation, a bounce cascade (find descendants by ancestry, close their PRs, re-queue them), a depth cap, and changes to the plan, implement and resolve-conflicts skills.
About 3 days of work behind a flag.

**What already exists** GitHub merge queue, GitLab merge trains and Uber's SubmitQueue run CI on combinations of PRs that are already approved.
They test, they do not write new code.
GitHub stacks, Graphite and ghstack are straight-line stacks that people write by hand.
A d4b.dev post (2026-08-28) has an agent stack PRs from Linear dependencies, but it has no rule for bounces.
The wedge: agents write new work on unreviewed parents, along the dependency graph, and a bounce cancels the children automatically.
Web search was available.
**Corrected tier:** 3, claimed 5.
Jacques has done it by hand and GitHub ships stacks, so "agent work must start from reviewed trunk" is already broken in practice for a one-person repo.

**The load-bearing risk** Nobody knows how often a Marshall car built on another Marshall car gets bounced because of its parent (n=0).
The 0 bounces in 15 cars so far come from one-line fixes and hand-built cars, and Marshall stopped 11 of its 20 claims before they parked.

**Cheapest proof** One week.
Day 1: in a scratch repo, check that merging a tip PR marks its ancestor PRs as merged, because `sweepDone` depends on that.
Days 2 to 4: build the pick rule, `base_ref` and the bounce cancel behind a flag.
Days 5 to 7: give Marshall a graph of 6 to 8 linked issues, about 8 runs.
Stop if a bounce traces back to a parent, a merge lands in a dead branch, or rebuild time is more than the wait it removes.

## Tier 4 - Earned auto-merge

> Marshall keeps a score for each kind of issue; a kind that Jacques keeps merging clean earns auto-merge with spot checks, and one bad result takes that away.

**Today** The implement skill says "Never merge the PR", so every PR waits for Jacques.
A replay of the DB gives 20 claims: 9 reached Needs Verification, 9 merged, 0 closed, 0 human bounces, 0 reverts, and 11 stopped at Blocked.
`claims.bounces` is 1 on 7 of the merged lots, but those were re-pickups after `classifier_failed`, not human rejections (`consider`, `src/scheduler/tick.ts:182`).

**Instead** The generators proposed ANSI Z1.4 switching rules.
The research changed this to Dodge CSP-1 (MIL-STD-1235), which works per unit instead of per lot: inspect 100% until i units in a row are clean, then inspect a random fraction f, and go back to 100% on one defect.
The class is the plan model in `claims.model` (opus = simple, fable = complex) combined with the top-level directory.
"Clean" must not be the merge click.
Clean = merged at the head SHA that Marshall pushed, after the hand-off existed, with no `Fix` commit on its lines within 14 days.
Blame survival today: TOD-5 434 of 470 lines, TOD-15 460 of 463.
Shadow mode comes first: emit `master.verdict` {class, sha, wouldMerge} and add one line to the hand-off.
The first rung is small: an ntfy `view` action that opens the PR for a one-tap merge.

**Standing on** The `events` table (`master.pr_merged`, `master.done`), `claims.model`, `ClassificationSchema` in `src/plan/classify.ts`, `PUSH_EVENTS` in `src/notify.ts`, `finishClaim` in `src/scheduler/store.ts`.

**Why now** Marshall has kept a full record since its first day, but the history this needs is being destroyed now: `finishClaim` wipes it, and no head SHA is stored.
Recording it now starts the clock.

**The hard part** Calibration with late and missing labels.
Under reduced inspection, only the samples and late signals (reverts, fix commits) catch a bad merge.

**What it needs that does not exist yet** The head SHA at every Marshall push, a `master.verdict` event, a blame-survival check 14 days after merge, and an escape detector.
TickTick has no CI and no branch protection, so "CI red on `master`" is not available as a signal.

**What already exists** Renovate auto-merges by fixed update type, gated by Merge Confidence.
So class-based auto-merge exists, but its classes are fixed and nothing demotes them.
GitHub Copilot coding agent goes the other way: the approval of the person who asked for the PR does not count.
The arXiv paper 2609.37985, "Merged, Not Measured", found that acceptance follows the agent's history in the repo (33% → 84%), and that 9 of 30 merged fixes gave no gain or made things worse.
claude-code issue #79107 asked for an advisory trust score and was closed "not planned".
The wedge: switching per class, automatic demotion, and a label that is not the merge click.
Web search was available.
**Corrected tier:** 4.
The original assumption ("trust is all or nothing") is false because Renovate exists, and the real bet is about the label.

**The load-bearing assumption** Everyone believes a human must approve every agent PR, and that a merge means approval.
The research showed that the second half is the real bet: this only works if one human's merges measure quality.
Evidence against: TOD-5 merged five minutes before its hand-off existed, ChessBuddy PRs 40, 41 and 42 merged 11 to 12 seconds apart with zero reviews and zero files marked viewed, and every agent commit has "Jacques Attinger" as its author.
Evidence for: blame survival on TickTick is 92% to 99%.

**Who else has tried** Renovate (fixed classes, no demotion), the "Merged, Not Measured" authors (they measured the gap but built no rule), and claude-code #79107 (asked for a score, closed).
No tool found has a self-demoting per-class rule for agent PRs.

**The load-bearing risk** The inspector and the escape detector are the same tired person.
Under reduced inspection, no signal is left to demote a class, so the ledger only confirms itself.
The timeline is also long: at 2 lots per 11 days, ten clean lots plus the 14-day window take about 10 weeks (mid-December), and TickTick has one class only (13 of 13 complex).

**Cheapest proof** Two days, about $0 in tokens, and 1 hour of Jacques's time.
Store the head SHA at each push and emit shadow verdicts.
Then Jacques blind re-reviews 5 merged agent PRs.
Stop if 1 or more has a defect he would now reject: then the merge click is not a usable label, and the idea needs a different label first.

## Tier 5 - Nothing to write (research moved it to tier 3)

> Marshall finds tasks Jacques already named in his own words, builds them while he sleeps, and he only says yes or no to the finished PR.

**What moved** The generator proposed mining Jacques's Claude Code chats for "later" tasks.
The measurement defeated that source.
In 14 days of ChessBuddy and TickTick sessions there were 53 typed turns, 8 regex hits and 1 real hit.
Of 15 hand-judged lines, 7 were noise, 4 were done in the same session, 3 went to Google Calendar, and 1 was a vague deferral.
That is 0 to 1 "would file" items per two weeks: Jacques does a task at once or puts it in his calendar.
The supply is somewhere else: 31 "Follow-ups proposed" bullets across 10 hand-off files, about 23% of them duplicates.

**Today** The hand-off package lists "Follow-ups proposed" (`plugin/skills/handoff/SKILL.md`).
`fileFollowUps` is off (`src/config.ts:63-69`), so the bullets go nowhere.
Plan §16.1 says the Innovate agent "never writes to Linear… A human yes sits between 'idea' and 'issue'" (`docs/project_marshall_plan.md`).

**Instead** Each follow-up bullet in the hand-off becomes a checkbox.
Jacques's tick is the human yes, so §16.1 holds.
A tick builds one PR (at most one opus run per day, inside `dailyStartCap`) and parks it in a `Speculative` state with a three-line ntfy push: his words, the diffstat, and the link.
If nobody touches it for 7 days, Marshall closes the PR and deletes the branch.
Transcript quotes are used only to rank and dedupe.
If transcripts are ever used, filter them: exclude Marshall's own sessions by `runs.session_id` (all 42 Marshall sessions log as `origin.kind:"human"`, and the resume prompt in `src/phases/names.ts:32` logs as typed text), and strip `<pasted_content>` (9 of 53 turns, 2 with third-party text).

**Standing on** `plugin/skills/handoff/SKILL.md`, `fileFollowUps` in `src/config.ts`, `dailyStartCap` in `marshall.config.json`, `TERMINAL_CLAIM_STATES` in `src/scheduler/types.ts`.

**Why now** Step 11 (the Innovate agent and its proposal store) is not built yet, and this changes where its input comes from.
The budget is idle: 20 starts in 13 days, 10 days at zero, and `dailyStartCap` never binds.

**The hard part** Attention cost.
A hand-off runs 574 to 2,031 words (median about 930, about 4 minutes plus the diff).
Jacques's cost to file an issue today is one sentence to Claude: CHE-6 to CHE-12 and TOD-21 were drafted by Claude from asks of 10 to 70 words.

**What it needs that does not exist yet** A pulse step that reads ticked checkboxes on the hand-off comment (its ID is already in the `.json` sidecar), a `Speculative` state, and auto-close after 7 days.

**What already exists** Cursor Bugbot Autofix opens fixes that nobody asked for (more than 35% merged), but only on an open PR.
Cursor and Codex automations queue scheduled agent results.
Linear Triage Intelligence dedupes.
Transcript extractors mine `~/.claude/projects` for memory, not for tasks.
The wedge: nothing turns a developer's own stated intent into a parked PR that expires by itself.
Web search was available.

**The load-bearing assumption** Everyone believes an agent must wait for an explicit hand-off (assign, @mention, prompt) before it spends effort.
For chats, this run measured the belief and found it safe for Jacques, because he states almost no deferred tasks.
For tickable follow-ups the belief does not apply, because the tick is the hand-off.
So no tier 5 idea survived at this slot.

**Who else has tried** Cursor Bugbot Autofix and scheduled automations do unasked work from code scans, not from what the developer said.

**What the product becomes** If the follow-up supply grows, Marshall stops being a queue that Jacques feeds and becomes a supply of finished options that he picks from.
It would then compete for his attention, not with other agents.

**What would have to be true** Most fragile first:

1. A three-line push costs Jacques less attention than writing the issue.
2. Jacques ticks at least 3 follow-ups a week.
3. At least a third of the ticked builds merge.

**How you would know within a month** One week is enough.
Render "Follow-ups proposed" as checkboxes, let each tick build one PR and send the three-line push, and log the seconds from push to merge or close.
Stop if there are fewer than 3 ticks, the merge rate is under 1 in 3, or the median decision takes more than 60 seconds.
Run the transcript regex read-only in parallel, and drop chat mining for good if it finds fewer than 3 "would file" items.
**Corrected tier:** 3.

## How this was made

4 recon agents over the repo, 5 generators on the absent product, ceiling removal, latent asset, inversion and transplant lenses, and 6 strengthen agents (one extra for the idea that replaced footprint locks).
Web search was available to every strengthen agent.
Lenses not used this run: why now, compounding moat, trust and guarantee.
No idea survived at tier 5.
Both tier 5 candidates (chat mining and the train) turned out easier than claimed, because Jacques's own behavior already breaks the assumption that each one tested.
